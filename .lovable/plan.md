
# Complete Self-Hosted VMS Deployment (DEV) — Single Port 80

## How the ports actually work

Inside the server, each service listens on its own port (bound to `127.0.0.1` only, not exposed to the LAN):

```
Container / process              Internal port    Exposed to LAN?
─────────────────────────────────────────────────────────────────
Supabase Kong (REST/Auth/etc.)   127.0.0.1:8000   NO
Supabase Studio                  127.0.0.1:3000   NO
Postgres                         127.0.0.1:5432   NO
Node middleware (SAP)            127.0.0.1:3002   NO
Nginx                            0.0.0.0:80       YES  ← only public surface
```

**Nginx on port 80 is the single entry point.** It reverse-proxies every path to the right internal port. So from a browser there is only **one URL and one port**: `http://10.200.1.7/...`.

```
Browser → http://10.200.1.7/...
                │
                ▼
        nginx :80 routes by path
                │
   ┌────────────┼─────────────┬───────────────┐
   ▼            ▼             ▼               ▼
   /            /supabase/    /api/           /studio/
 SPA           Kong :8000    Middleware :3002  Studio :3000
 (dist/)      (REST,Auth,    (SAP proxy)      (admin UI)
              Storage,
              Realtime,
              Functions)
```

So when the React app calls Supabase, it calls `http://10.200.1.7/supabase/auth/v1/...` — nginx strips `/supabase/` and forwards to Kong on `:8000` internally. The browser **never** talks to `:8000` directly. That is what the user means by "supabase port is 8000" — it stays 8000 inside the box; outside the box everything is 80.

Studio gets the same treatment: served at `http://10.200.1.7/studio/` via nginx (protected by HTTP basic auth so randoms on the LAN can't reach it).

## Deliverables (new files in this repo)

1. **`scripts/deploy-vms-server.sh`** — one master script. Idempotent. `sudo bash` runs everything below.
2. **`scripts/lib/`** — modular helpers sourced by the master:
   - `00-preflight.sh` — root + Ubuntu check, ensure VMS dirs exist, tee log to `DEV/VMS/logs/deploy.log`
   - `10-packages.sh` — apt base, Node 20 (NodeSource), Docker Engine + Compose plugin, nginx, ufw, jq, openssl, git, rsync, python3, apache2-utils (for htpasswd)
   - `20-supabase.sh` — clone `supabase/supabase` `docker/` into `DEV/VMS/backend/` (skip if exists); generate `backend/.env.secrets` once (POSTGRES_PASSWORD, JWT_SECRET, ANON_KEY, SERVICE_ROLE_KEY, DASHBOARD_USERNAME/PASSWORD, vault keys, Logflare tokens, POOLER_TENANT_ID); write `backend/.env` with `SITE_URL=http://10.200.1.7`, `API_EXTERNAL_URL=http://10.200.1.7/supabase`, `SUPABASE_PUBLIC_URL=http://10.200.1.7/supabase`, ports forced to `127.0.0.1:8000 / 3000 / 5432`; `docker compose pull && up -d`; wait for Kong on `127.0.0.1:8000`
   - `30-migrations.sh` — apply `DEV/VMS/supabase/migrations/*.sql` via `docker compose exec -T db psql -U postgres -d postgres -f -`; tracks applied filenames in `public._applied_migrations` for re-run safety
   - `40-functions.sh` — `rsync DEV/VMS/supabase/functions/ backend/volumes/functions/`; `docker compose restart functions`
   - `50-middleware.sh` — `npm ci --omit=dev` inside `middleware/`; write `.env` from `.env.example` + values (SAP_BP_API_URL, SAP creds prompted on first run, auto-gen `MIDDLEWARE_SHARED_SECRET`); install + enable `vms-middleware.service` on `127.0.0.1:3002`
   - `60-frontend.sh` — write `.env.production` (`VITE_SUPABASE_URL=http://10.200.1.7/supabase`, `VITE_SUPABASE_PUBLISHABLE_KEY=<ANON_KEY>`); `npm ci && npm run build`; rsync `dist/` → `DEV/VMS/frontend/dist/` (matches your existing nginx `root`)
   - `70-nginx.sh` — **edit `/opt/Ramky_Applications/nginx/ramky-vms.conf` in place** (`.bak` saved). Preserves your `server_name`, `root`, `logs`, `/uploads/`, `try_files`, `client_max_body_size`. Fixes/adds these `location` blocks:
     - `/api/`        → `http://127.0.0.1:3002/`   (middleware — was incorrectly pointing to 3000)
     - `/supabase/`   → `http://127.0.0.1:8000/`   (Kong) with WebSocket upgrade headers for Realtime
     - `/studio/`     → `http://127.0.0.1:3000/`   protected by `auth_basic` using `/etc/nginx/.vms-studio.htpasswd` (created from `DASHBOARD_USERNAME/PASSWORD`)
     - `client_max_body_size 100M` kept; WebSocket headers added globally for `/supabase/`
   - Then `nginx -t && systemctl reload nginx`
   - `80-firewall.sh` — `ufw allow 22, 80`; 3000/8000/3002/5432 stay private
   - `90-summary.sh` — print URLs, credentials, log paths, next steps

3. **`scripts/templates/vms-middleware.service`** — systemd unit
4. **`scripts/README-DEPLOY.md`** — runbook (same as "After setup" below)

## How you use it

On your **dev machine** (this repo):
```bash
rsync -av --delete \
  --exclude node_modules --exclude dist --exclude .git \
  ./ root@10.200.1.7:/opt/Ramky_Applications/DEV/VMS/source/
```

On the **server**:
```bash
ssh root@10.200.1.7
cd /opt/Ramky_Applications/DEV/VMS/source
sudo bash scripts/deploy-vms-server.sh
```

First run: ~5–10 min. Re-runs are safe (secrets not regenerated, migrations not re-applied).

Useful flags:
```
--skip-docker      # don't reinstall docker/node/nginx
--skip-build       # use existing dist/
--skip-migrations  # skip SQL apply
--skip-functions   # skip edge-fn sync
--skip-nginx       # don't touch nginx config
--reset-secrets    # regenerate .env.secrets (DANGEROUS — invalidates JWTs)
```

2. **Open `http://10.200.1.7/studio/`** — log in with the dashboard creds. Create the first admin user under Authentication → Users.

## Technical notes

- **Single public port (80).** Everything Supabase-related goes through nginx → Kong. The frontend is built with `VITE_SUPABASE_URL=http://10.200.1.7/supabase` so the browser never touches `:8000` directly. No CORS surprises because everything is same-origin.
- **WebSocket / Realtime** works because the `/supabase/` location adds `Upgrade` and `Connection: upgrade` headers.
- **Studio is gated** by HTTP basic auth on the nginx side (the dashboard creds also become the htpasswd entry). Postgres / Kong / Studio / middleware never bind to `0.0.0.0`.
- **No SSL** — HTTP only, as agreed. Adding HTTPS later = Certbot against `dev-vms.ramky.com`, no other changes.
- **No app source changes** — only new files under `scripts/` and a controlled in-place edit of `/opt/Ramky_Applications/nginx/ramky-vms.conf` with a `.bak` backup.
- **Re-runs only rebuild what changed** — secrets generated once, migrations tracked, frontend build cached by Vite.
