# Verify and Correct the Running Production Reset Function

## Confirmed finding

The Production source pasted here contains `password-reset-direct-portal-v2` and cannot send the authentication service's `/auth/v1/verify` URL. It always extracts the recovery token and builds:

`https://vyapaar.ramky.com/reset-password?token_hash=...&type=recovery`

Therefore, a newly received `/auth/v1/verify` link is not being generated by this pasted code. The likely deployment mismatch must be confirmed against the running Production container rather than only the source file.

## Plan

1. **Compare all three Production copies**
   - Check the repository file under the Production source directory.
   - Check the deployed file under `backend/volumes/functions/send-password-reset/index.ts`.
   - Check `/home/deno/functions/send-password-reset/index.ts` inside the running functions container.
   - Confirm all three contain `password-reset-direct-portal-v2` and have matching checksums.

2. **Confirm the Production request reaches the intended service**
   - Verify the Production browser calls the Production `/supabase/functions/v1/send-password-reset` endpoint.
   - Confirm the request includes `redirectTo=https://vyapaar.ramky.com/reset-password`.
   - Inspect the functions log for the fresh request to rule out another server or stale Production instance.

3. **Correct any deployment mismatch**
   - Sync the latest repository function into the Production functions volume.
   - Set the Production public URL to `https://vyapaar.ramky.com`.
   - Force-recreate both authentication and functions services so no older worker remains loaded.
   - Abort if the file inside the recreated container lacks the direct-portal marker.

4. **Verify using a newly requested email**
   - Request a new password-reset email only after the restart.
   - Confirm its button and fallback text both use the Production `/reset-password?token_hash=...&type=recovery` URL.
   - Confirm neither `vendx.ramky.com` nor `/auth/v1/verify` appears.
   - Open the link and confirm the new-password form is displayed.

## Important distinction

The Quality code is older and can fall back to `action_link`, but Quality currently works because its authentication response supplies `hashed_token`. The Production code is safer and removes that fallback. Replacing Production with the older Quality code would reintroduce the possibility of the wrong hostname and is not the fix.
